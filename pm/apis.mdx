## Introduction

### Why this repo exists

This is a fork of [actualbudget/actual](https://github.com/actualbudget/actual) kept for one
purpose: to run **this operator's own money** on their own machine, with their own decade of bank
statements in it, driven from wherever they happen to be working. Upstream Actual is an excellent
web app. It is a web app, though, and the operator does not live in a browser. They live in a
terminal and in Claude Code.

So this fork grows two extra front doors — a CLI (`abx`) and an MCP server (`actual_budget`) — and
both of them need the same thing: **a way to ask the running app a question, and a way to tell it to
do something, that is not a browser.**

That is this spec.

### Where this spec fits under that umbrella

Three specs, one stack:

```
                       ┌──────────────────────────────┐
   web browser ───────▶│                              │
   `abx` (cli.mdx) ───▶│   /machine/v1   apis.mdx     │──▶ @actual-app/api ──▶ the budget
   MCP  (mcp.mdx)  ───▶│   ← THIS SPEC                │       (one instance)
                       └──────────────────────────────┘
```

[cli.mdx](./cli.mdx) says what the terminal surface looks like. [mcp.mdx](./mcp.mdx) says what the
agent surface looks like. **This spec says what is behind both of them**, and it is deliberately
written first among equals: a verb that `abx` cannot serve, and a tool the MCP cannot serve, are
both the same bug — a missing route here.

cli.mdx §5 introduced the machine plane with a fifteen-row route table and the sentence _"the
route-by-route reference lives with the server."_ **This spec is that reference**, and it has grown
well past fifteen rows, because the question it now answers is not "what does `abx` need" but
"what can a person do in the UI."

### What the operator gets from it

Concretely, on a Tuesday evening:

- _"How much did I actually spend on groceries this year, by month?"_ — one route, the engine's own
  aggregation, no model arithmetic anywhere in the chain.
- _"Create the 27 accounts in my statement archive and import all 12,007 transactions."_ — a
  manifest route, a provisioning route, and Actual's own importer deciding every duplicate.
- _"I overspent Dining by $84. Cover it from Fun Money."_ — one route, the same one the UI's little
  overspend arrow calls.
- _"Northbank says $4,211.08 as of the 31st. What do I say?"_ — a reconcile route that returns the
  difference and, only if asked again, writes the adjustment.
- _"Undo that."_ — a route, because an agent that can write must be an agent that can be un-written.

### How it works — the idea

**One engine, three faces.** The sync server is the only long-running Node process in the repo, so
the plane mounts there and holds one initialised `@actual-app/api` instance for the process
lifetime. Every balance the browser shows, every number `abx` prints, and every figure the MCP hands
a model comes out of that one instance. There is no second implementation of anything to drift.

**The filesystem is the authentication.** The app mints a 256-bit random key into a 0600 file in the
operator's home directory. A caller that can read that file is already a process running as the
operator on the operator's machine — at which point it could read the budget database directly. The
key is not trying to stop that person. It is stopping _everything else_: the other user on the box,
the web page the operator happens to have open, the container on the same host.

**Nothing computes twice.** The clients are thin on purpose (cli.mdx §5.4, mcp.mdx §9.4). If a
question needs arithmetic, the arithmetic happens here, once, in the engine — and that is why this
spec has an analytics plane (§10) and a reconcile route, which upstream computes in React.

### How it works — the machinery

An `abx` or MCP call is:

1. HTTP to `127.0.0.1:5006/machine/v1/...` with an `X-Actual-Machine-Key` header.
2. Five gates in order — loopback, origin, key, tier, input schema (§4.4, §16).
3. A handler that validates its arguments, calls **one** engine operation, and returns.
4. One JSON envelope, success or failure, always the same shape (§5).

Writes add a sixth step in front: the caller must first call the matching `plan` route, read the
`confirm_token` it returns, and echo it back (§7).

### What this spec covers

The auth model; the envelope; the tier model; the write protocol; the complete route catalogue
family by family; a coverage matrix against the web UI; the analytics plane; the ingest plane and
its manifest-driven account provisioning; the query escape hatch; the money and date rules; limits,
concurrency, security, open-source safety, testing, use cases, acceptance criteria and build phases.

It does not cover argument parsing or terminal rendering (cli.mdx §7, §13), tool descriptions or
model-facing prompt design (mcp.mdx §9, and [ai/mcp_prompt.md](../ai/mcp_prompt.md)).

## Goal

> **Everything a person can do in the Actual Budget web UI, a program can do over this plane — with
> the same engine computing it, the same importer deciding duplicates, and three switches plus a
> token standing between an agent and the operator's real money.**

Four halves to that sentence, and each is a rule the build is measured against:

| Half                           | The rule                                                                                                                          |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------- |
| **Everything the UI can do**   | §9's coverage matrix has a row per UI action and a route per row. A blank cell is a backlog item, never a shrug.                  |
| **The same engine**            | No route reimplements a calculation the app already does. Where upstream computes in React, the calculation **moves** here (§10). |
| **The same importer**          | Duplicate detection is `importTransactions` with `dryRun`, never a lookup we wrote (§11.6).                                       |
| **Three switches and a token** | Server tier, client tier, `dry_run: false`, and a `confirm_token` the caller can only have read from a plan (§7).                 |

## 2. The ten design rules

Each of these has shown up as a real bug in a real finance tool. They are stated once, here, and
every route in §8 is written to obey them.

**R1 — One engine call per route.** A route validates, calls one engine operation, and renders. A
route that needs two calls is either two routes or one new engine operation. The exception is
explicitly-named **composed routes** (reconcile, ingest apply, batch), which say so in their entry
and carry a `composed: true` flag in `meta`.

**R2 — Money is an integer number of cents.** Every amount in every argument, every response field
and every intermediate value. Never a float, never a string, never "dollars just for this one".
§14.1.

**R3 — Absent is not zero.** A category with no budget entry returns `budgeted: null`, not `0`. A
balance we could not compute is an error, not `0`. §14.2.

**R4 — Every write has a dry run.** `dry_run` defaults to **true** on every write route where a
preview is meaningful. The preview is produced by the same code path as the write, with one boolean
different — never by a second function that predicts it. §7.2.

**R5 — Every cap is reported.** A result that was clamped carries `meta.truncated: true` and
`meta.limit_applied`. A silent cap is how a caller concludes an account has exactly 1,000
transactions. §5.5.

**R6 — Every error names a fix.** `error.hint` is a remediation the caller can act on, in the
caller's own vocabulary. "Invalid input" without a hint is a bug report waiting. §5.4.

**R7 — The app decides, we report.** Where the app has an opinion — what is a duplicate, what a rule
does to a transaction, what a category's balance is — the route returns the app's verdict verbatim
and adds nothing. §11.6.

**R8 — Reads never mutate.** No route in the read tier writes to the budget, the filesystem or the
sync log. `POST /query` is a read because ActualQL is guarded to `SELECT`. `POST /ingest/scan` is a
read because it only stats files. Anything that touches disk says so in its entry.

**R9 — Fail closed.** No key, no plane. No tier, no route. No schema match, no handler. An
unauthenticated or untiered fallback does not exist anywhere in this design, and a 404 is the answer
to everything the caller was not supposed to reach.

**R10 — The plane is loopback-only, forever.** There is no configuration that binds it to another
interface, and no flag that turns the origin gate off. Remote access to a budget is what the sync
server is for; it has its own auth and it is not this. §16.

## 3. Placement, layout and build integration

### 3.1 Directory layout (LOCKED)

```
packages/sync-server/src/machine/
├── index.ts                 router assembly + initMachinePlane()   ← exists
├── credentials-file.ts      the key: mint, resolve, fingerprint    ← exists
├── machine-auth.ts          gates 1–3                              ← exists
├── envelope.ts              ok/error envelope + error vocabulary   ← exists
├── engine.ts                the single @actual-app/api instance, lifecycle, health
├── tier.ts                  gate 4 — read / write / admin
├── validate.ts              gate 5 — hand-written validators, one per route
├── route.ts                 the RouteDef shape + the /capabilities projection
├── confirm.ts               gate 6 — plan tokens, ceilings, the write protocol
├── money.ts                 cents in, cents out; the ONE conversion point
├── routes/
│   ├── plane.ts             ping · whoami · capabilities · health
│   ├── planned.ts           declared-but-unbuilt routes (§6.3a)
│   ├── budgets.ts           budget files, backups, sync
│   ├── accounts.ts          accounts, groups, close/reopen, reconcile
│   ├── transactions.ts      transactions, splits, bulk, merge, move, export
│   ├── categories.ts        categories and groups
│   ├── budget.ts            the envelope operations and goal templates
│   ├── reference.ts         payees · tags · rules · schedules · notes
│   ├── analytics.ts         §10
│   ├── ingest.ts            §11 and §12
│   ├── query.ts             §13
│   └── admin.ts             the destructive tier
└── *.test.ts                colocated
```

**`validate.ts`, not `schema.ts`.** An earlier draft of this spec called it
`schema.ts`; `/schema` is also a route — the one describing the AQL tables `/query` may name — and
two different things called "schema" one directory apart is a question every future reader has to
stop and answer.

**The engine is a DYNAMIC import of a devDependency, not a dependency (LOCKED).**
`@actual-app/sync-server` is published. Making `@actual-app/api` a runtime dependency of it changes
an upstream artefact's dependency graph, which is the merge friction this layout exists to avoid —
the whole delta is meant to be one `app.use()` and one `initMachinePlane()`. So `engine.ts` reaches
it with `await import(specifier)` through a variable (vite leaves it external), and a deployment
without it — a production `yarn install:server`, which installs no devDependencies — gets a plane
that reports the engine as unavailable and says so. That is R9, fail closed, not a degraded mode.

The failure is **diagnosed, not merely caught**: "not installed" and "installed but not built" are
different problems with different fixes, and a blanket `catch` that reports the first for both sends
an operator to install something they already have. The distinction is on `ERR_MODULE_NOT_FOUND`
plus whether the unresolved path is inside `dist/`.

**Why inside `packages/sync-server/` and not outside it like `cli/`.** `abx` lives outside
`packages/` so an upstream merge can never touch it (cli.mdx §1.4). This plane cannot: it must be
mounted by `app.ts`, which is upstream's file, and it must import loot-core's engine. It lives
under `src/machine/` as **one directory with one mount point**, so the entire delta to upstream's
tree is one `app.use()` line and one `initMachinePlane()` call — a merge conflict surface of two
lines rather than two hundred.

### 3.2 Build integration

`just build` already builds every workspace plus the CLI. The plane is part of
`@actual-app/sync-server` and needs no separate step. `just server-bg` arms it; the boot line
`Machine plane armed on /machine/v1 (key 4f2a…/sha256:9c1b, writes ENABLED)` is the operator's proof
it is up.

## 4. Authentication — the machine key

This section is the **authority**. cli.mdx §4 and mcp.mdx §6 restate parts of it for their own
readers; where they differ, this text is correct.

### 4.1 Why not a password (LOCKED)

The sync server already has a password. It is the wrong credential for this plane, for three
reasons, each fatal on its own:

1. **It is the operator's, typed by a human.** A CLI that prompts for a password is a CLI that
   cannot run in a loop, and an MCP server that prompts is an MCP server that hangs a conversation.
2. **It unlocks the wrong thing.** The sync password authorises _sync_ — pulling and pushing budget
   files for any device. This plane authorises _this machine's_ engine. Reusing one credential for
   both means a leaked one loses both.
3. **It is a shared secret with a remote.** The whole point of the machine key is that it never
   leaves this computer, so its blast radius is this computer.

### 4.2 Shape and entropy (LOCKED)

> **32 bytes from `crypto.randomBytes()`, rendered as 64 lowercase hex characters.**

- **256 bits of entropy.** A UUIDv4 carries 122 random bits. This is **more than twice** that, and
  it is not a UUID on purpose: a UUID _looks_ like an identifier, and identifiers get logged, put in
  URLs, and pasted into issues. A 64-character hex string looks like a secret and gets treated like
  one.
- **`crypto.randomBytes` and nothing else.** `Math.random()` is a PRNG seeded from wall-clock-ish
  state and is not cryptographically secure; `crypto.randomUUID()` would be, but see above. A test
  asserts the mint path imports `node:crypto` and that no `Math.random` appears anywhere in
  `src/machine/`.
- **Validated on every read.** `/^[0-9a-f]{64}$/`. A key that does not match this is refused at
  resolve time with the rotate command as the hint — never silently padded, trimmed or lowercased.
- Guessing it at a million tries a second from a process that could reach the port anyway takes
  about 3.7 × 10^63 years. It is not the attack you need to worry about, and that is the point.

Code: `packages/sync-server/src/machine/credentials-file.ts` — `mintKey()`, `isWellFormedKey()`

### 4.3 Where it lives (LOCKED)

```jsonc
// ~/.credentials/actual_budget.json          mode 0600, directory mode 0700
{
  "actual_budget": {
    "machine": {
      "api_key": "4f2a…64 hex chars…",
      "created": "2026-09-20T18:04:11.902Z",
      "created_by": "sync-server", // or "abx" or "mcp" — whoever needed it first
      "label": "bryan-macstudio",
    },
    "statements": { "root": "/…/bank_statements" },
  },
  // …other products' top-level keys, which we preserve byte for byte
}
```

- **`~/.credentials/`, not the repo.** The repo is going public (§17). There is no config key
  anywhere in the tree that can hold this value.
- **Per machine, never synced.** Not in Dropbox, not in a dotfiles repo, not in `1Password`
  (nothing needs to read it but processes on this box). A second machine mints its own.
- **The write merges.** Other products share `~/.credentials/`. A writer that serialises the file
  whole from memory is the program most likely to delete somebody else's secret at 2am, so the write
  reads, mutates one subtree, and writes back — preserving every key it does not own.
- **The write is atomic and refuses symlinks.** Temp file in the same directory, `O_EXCL`, `fsync`,
  `0600` from creation rather than `chmod` afterwards (a file that is briefly 0644 is a file that was
  briefly readable), then `rename`. If the destination is a symlink, the write is abandoned — that
  is somebody redirecting our secret, not a convenience.

### 4.4 Who mints it, and when (LOCKED)

**Whichever of the three processes needs it first, and exactly once.**

The intended path is that **the web app mints it for itself, with no operator action at all**:
`initMachinePlane()` runs inside `run()` at server boot, resolves the key, finds none, and mints one.
By the time the operator first types `abx` or first asks Claude Code a question, the key is already
there, and neither of them had to be told about it.

Three rules make that safe:

1. **Mint at boot, never at import.** Resolving the key _creates_ one. Doing that at module scope
   means every test that imports the module writes a secret into the developer's real home
   directory as an invisible side effect. `machineRouter` is created at import and holds no key;
   `initMachinePlane()` arms it from `run()`.
2. **The mint is a compare-and-set.** The writer re-reads inside the write and yields if a key
   appeared, then reads back and trusts the file rather than its own mint. Three processes starting
   at once converge on one key instead of three.
3. **Until it is armed, the plane 404s everything** (R9). Not 500, not "auth disabled" — 404, the
   same answer a stranger gets, so probing it teaches nothing.

`abx key init` and `abx key rotate --yes` exist for the operator who wants to do it deliberately;
they are conveniences over the same code path, not a separate one.

### 4.5 Resolution order (LOCKED)

First hit wins:

| #   | Source                                                                 | For                                               |
| --- | ---------------------------------------------------------------------- | ------------------------------------------------- |
| 1   | `ABX_MACHINE_KEY` / `ABMCP_MACHINE_KEY`                                | CI, one-off overrides. Never in a checked-in file |
| 2   | `ABX_MACHINE_KEY_FILE` / `ABMCP_MACHINE_KEY_FILE`                      | the Docker-secret shape                           |
| 3   | `~/.credentials/actual_budget.json`                                    | **the normal path**                               |
| 4   | mint one (servers only; `abx`/MCP mint only on an explicit `key init`) | first run                                         |

`ABX_CREDENTIALS_FILE` / `ABMCP_CREDENTIALS_FILE` relocate step 3 — that is the seam every test
uses, and it is why no test touches a real home directory.

### 4.6 How it is sent, and how it is checked (LOCKED)

```http
POST /machine/v1/transactions HTTP/1.1
Host: 127.0.0.1:5006
X-Actual-Machine-Key: 4f2a…
Content-Type: application/json
```

- **A header, never a query parameter.** Query strings land in access logs, shell history, and the
  `Referer` of anything the page loads.
- **`X-Actual-Machine-Key`, not `Authorization: Bearer`.** Proxies, browser devtools and HTTP
  libraries all have special handling for `Authorization` — auto-forwarding on redirect, credential
  managers, "remember this". A bespoke header gets none of that helpfulness.
- **Constant-time comparison, safe on unequal lengths.** `timingSafeEqual` _throws_ on a length
  mismatch, so the obvious guard `a.length === b.length && timingSafeEqual(a, b)` leaks the length
  through timing and is itself an oracle. Both sides are hashed to a fixed-width digest first, and
  one comparison of equal-length buffers always runs.
- **The 401 body is constant.** `{"ok":false,"error":{"code":"unauthorized"}}` — byte for byte the
  same for a missing key and a wrong one. The server keeps its silence; the _client_ does the
  explaining, because the client knows which file it failed to read and the server does not know who
  is asking.

### 4.7 The gate ladder (LOCKED)

Order is load-bearing. Nothing below a gate runs until it passes.

| #   | Gate              | Refuses                                          | Answer                           |
| --- | ----------------- | ------------------------------------------------ | -------------------------------- |
| 1   | Loopback socket   | another computer                                 | `404`                            |
| 2   | Origin + Host     | a web page on this computer; DNS rebinding       | `404`                            |
| 3   | The key           | another user on this computer                    | `401`, constant body             |
| 4   | Tier              | a write with the tier off; admin from the MCP    | `403 write_disabled`/`forbidden` |
| 5   | Input schema      | a malformed or unknown argument                  | `400 invalid_input`              |
| 6   | Confirm + ceiling | a write with no token, a stale token, or too big | `403`/`409`                      |

**Two facts about the app this mounts inside that gates 1 and 2 must survive:**

1. **`app.set('trust proxy', …)` is global**, so `req.ip` is derived from `X-Forwarded-For` and is
   attacker-controlled. Gate 1 reads `req.socket.remoteAddress` — the kernel's view of the peer —
   and never consults `req.ip`, `req.ips`, `X-Forwarded-For` or `X-Real-IP`. A remote request
   carrying `X-Forwarded-For: 127.0.0.1` gets a 404, and there is a test that says so.
2. **`app.use(cors())` is global and permissive**, so "arrived on loopback" includes any web page
   the operator has open: `https://evil.example` can `fetch('http://127.0.0.1:5006/…')` and the
   packet really does come from the loopback interface. The key is what stops it. Gate 2 is the
   second wall so that is not one control deep — a browser always sends `Origin` or
   `Sec-Fetch-Site` and cannot be talked out of it, and `abx`, the MCP and `curl` send neither, so
   _presence_ is the signal. We do not need to recognise the attacker's origin, only that there is
   one. The plane also strips the `Access-Control-Allow-Origin` the app-wide `cors()` already added,
   and sets `Cache-Control: no-store` and `Vary: Origin`.

Gate 2 also pins the `Host` header, because DNS rebinding is precisely the trick that turns a remote
page into a loopback client, and the `Host` is what it has to lie about to get there.

### 4.8 Rotation, and what the key is not

**Rotation** is `abx key rotate --yes`: mint, merge-write, and print the new fingerprint. The
running server still holds the old one in memory, so the operator restarts it — and until they do,
every call returns `401` with the hint `restart the sync server`. That is a deliberately loud
failure; a plane that hot-reloads its own credential is a plane where a stolen key is revoked
"eventually".

**The fingerprint** — `4f2a…/sha256:9c1b`, the first four hex characters plus a SHA-256 prefix — is
the **only** representation of the key that may be logged, printed, put in an error, or shown to a
model. Two people can confirm they hold the same key without either of them exchanging one. A test
greps the built output for anything matching the key pattern.

**What the key is NOT:**

- Not a user identity. It authenticates _the machine_, not a person, and there is exactly one.
- Not a capability grant. Holding it does not enable writes; the tier switches do (§6).
- Not a sync credential. It cannot pull, push, or reach the sync server's own endpoints.
- Not an API key in the SaaS sense. It is never sent off this machine, ever, by anything.
- Not encryption. The budget's end-to-end encryption key is a different secret, owned by the app,
  and this plane never reads it, prints it, or accepts it as an argument.

## 5. The transport contract

### 5.1 The envelope (LOCKED)

Every response, success or failure, is one JSON object of the same shape.

```jsonc
// success
{
  "ok": true,
  "data": { /* route-specific */ },
  "meta": {
    "target": "local",
    "budgetId": "8c1e…",
    "budgetName": "Household",
    "serverVersion": "26.9.0",
    "asOf": "2026-09-20T18:41:02.118Z",
    "tookMs": 38,
    "truncated": false,
    "tier": "read"
  }
}

// failure
{
  "ok": false,
  "error": {
    "code": "not_found",
    "message": "No account with that id.",
    "hint": "GET /machine/v1/accounts",
    "details": { "id": "5a0e…" }   // optional, structured, never a stack
  }
}
```

**Casing (LOCKED — §5.1a).** Two conventions, and the split is principled rather than sloppy:

- **`meta` and `error` are OURS, and they are camelCase.** This is a TypeScript codebase and
  [mcp.mdx](./mcp.mdx) §12.1 already publishes `budgetId` / `serverVersion` / `asOf` / `tookMs`.
- **`data` is the ENGINE'S, verbatim, in the engine's own casing — which is snake_case**
  (`balance_current`, `account_group_id`, `is_income`, `group_id`). Renaming it would be a
  translation layer, and a translation layer is a second representation of every entity that can
  drift from the first. §2 R7 says the app decides and we report; renaming what it decided is not
  reporting it.
- **Arguments are snake_case**, matching both the engine's field names and the MCP's tool arguments,
  so `category_id` means the same thing in a filter, in a response and in a tool call.

- **`data` is never a bare array.** A list route returns `{ "accounts": [...] }`, so the shape can
  grow a `total` or a `cursor` later without breaking a caller that indexed into it.
- **`meta.budgetId` and `meta.budgetName` are on every response.** They are the cheapest possible
  defence against a caller that has drifted onto the wrong ledger: the evidence is in every reply.
- **`meta.asOf` is the server's clock.** A balance without a timestamp is a lie tomorrow.
- **`error.details` is structured and bounded.** Field names, counts, ids, the conflicting rows. It
  never contains a stack trace, a file path outside the statements root, or a SQL string — those go
  to the server's log and stay there (§16.4).

### 5.2 The nine codes (LOCKED)

`unauthorized` · `forbidden` · `not_found` · `invalid_input` · `conflict` · `write_disabled` ·
`not_ready` · `upstream_error` · `internal`

| Code             | HTTP | Means                                                                                                 |
| ---------------- | ---- | ----------------------------------------------------------------------------------------------------- |
| `unauthorized`   | 401  | gate 3 — no key or wrong key                                                                          |
| `forbidden`      | 403  | gate 4/5 — the tier or the guard says no (admin route, denied table)                                  |
| `not_found`      | 404  | gates 1–2, an unknown route, or a real missing entity                                                 |
| `invalid_input`  | 400  | gate 5 — schema, range, or an argument combination that cannot hold                                   |
| `conflict`       | 409  | the world changed under the caller — stale token, concurrent write, two statements claiming one month |
| `write_disabled` | 403  | gate 4 — a write route with the tier off                                                              |
| `not_ready`      | 503  | the app is up but no budget is loaded, or the plane is not armed                                      |
| `upstream_error` | 502  | the engine or the sync server failed in a way we can name                                             |
| `internal`       | 500  | anything else; the message is generic and the detail is in the log                                    |

**A tenth code is a spec change, not a commit.** mcp.mdx §12.3 lists twelve: the three extra
(`confirm_required`, `too_many_changes`, `wrong_server`) are minted by the MCP and **never appear on
this wire**. The relationship is one-way and total — every code here is also an MCP code, so the MCP
can pass a server error through unchanged. A test asserts the superset.

### 5.3 Versioning (LOCKED)

The path carries the version: `/machine/v1/`. Within `v1`:

- **Adding a route, an optional argument, or a response field is not a breaking change** and does not
  bump anything. Callers must ignore fields they do not know.
- **Removing or renaming anything, or changing a field's type or units, is `v2`.** There is no
  deprecation window inside a version; a `v1` route means what it meant.
- `GET /capabilities` (§6.3) is how a client discovers what this particular build has, so a newer
  CLI against an older server degrades with a clear message instead of a 404 it cannot interpret.

### 5.4 Errors name a fix (R6)

`hint` is written for the caller who will read it, and it is a _command or a decision_, never a
restatement:

| Bad hint              | Good hint                                                                   |
| --------------------- | --------------------------------------------------------------------------- |
| "Invalid account id." | `GET /machine/v1/accounts` — or pass `account_name` instead of `account_id` |
| "Write disabled."     | Set `ACTUAL_MACHINE_ALLOW_WRITE=1` on the server and restart it             |
| "Too many changes."   | 1,904 rows would change; raise `max_changes`, or narrow with `start`        |
| "Not ready."          | `abx up`, then retry                                                        |

### 5.5 Pagination, ordering and truncation

Every list route takes `limit`, `offset` and `order`; every one has a hard cap.

| Argument | Default | Cap   | Notes                                                      |
| -------- | ------- | ----- | ---------------------------------------------------------- |
| `limit`  | 200     | 5,000 | **Clamped, never rejected** — over the cap you get the cap |
| `offset` | 0       | —     | Stable only under a stable `order`                         |
| `order`  | route   | —     | `field` or `-field`; only fields the route documents       |

When a cap bound the result: `meta.truncated: true` and `meta.limit_applied: 5000`. A caller that
wants everything pages, and a caller that wanted a number should have asked §10 for the number.

**Ordering is always explicit and always total.** Every list route's default order ends with a tie
break on `id`, because a paginated list with a non-total order silently skips and repeats rows.

### 5.6 Idempotency

- Every `GET` is idempotent and safe.
- Every `POST` that creates something accepts an optional `idempotency_key` (any string up to 128
  characters). A repeat within the process lifetime returns the **original** response with
  `meta.replayed: true` rather than creating a second thing. This is what makes an agent's retry
  after a timeout safe.
- `PATCH` and `DELETE` on an id are naturally idempotent; a `DELETE` of something already gone is
  `ok: true` with `deleted: 0`, not a 404, so a retry loop terminates.

### 5.7 Request shape

`Content-Type: application/json` on every body-bearing call. Bodies are capped at **8 MiB** (an
import batch of 12,000 rows is about 2 MiB). Unknown top-level fields are **rejected**, not
ignored — a typo'd `start_date` that silently means "no filter" is how someone imports a decade into
one month.

## 6. Tiers, capabilities and negotiation

### 6.1 Three tiers

| Tier      | Server switch                  | What it is for                                                                                         |
| --------- | ------------------------------ | ------------------------------------------------------------------------------------------------------ |
| **read**  | always on                      | everything that computes and returns                                                                   |
| **write** | `ACTUAL_MACHINE_ALLOW_WRITE=1` | changes the ledger: transactions, budgets, accounts, rules, imports                                    |
| **admin** | `ACTUAL_MACHINE_ALLOW_ADMIN=1` | can lose data or change the install: delete an account, delete a budget file, restore a backup, rotate |

Admin is a separate switch and not "write plus". The two are held for different reasons at different
times: write is "I intend to let a program edit my budget this week"; admin is "I am doing surgery
right now and I am watching". **The MCP is never given the admin tier** — mcp.mdx §9.5 does not
expose an admin tool, this plane would refuse it anyway, and the refusal has its own code path with
its own test.

### 6.2 The client's switch is separate

The server's tier is necessary and not sufficient. `abx` requires `--write` on the call (cli.mdx
§7.1) and the MCP requires `ABMCP_ALLOW_WRITE=1` plus a per-call confirm (mcp.mdx §9.7). The plane
does not know or care which client is calling — **it enforces its own half and trusts nothing.**

### 6.3 `GET /capabilities` (LOCKED)

One read route returns the machine-readable route table of _this build_:

```jsonc
{
  "ok": true,
  "data": {
    "apiVersion": "v1",
    "serverVersion": "26.9.0",
    "tiers": { "read": true, "write": true, "admin": false },
    "budgetLoaded": true,
    "routes": [
      {
        "path": "/accounts",
        "methods": ["GET", "POST"],
        "tier": { "GET": "read", "POST": "write" },
        "status": { "GET": "live", "POST": "live" },
        "summary": {
          "GET": "Accounts, with balances.",
          "POST": "Create an account.",
        },
      },
      {
        "path": "/sync",
        "methods": ["POST"],
        "tier": { "POST": "write" },
        "status": { "POST": "planned" },
        "summary": {
          "POST": "Sync with the sync server. NOT IMPLEMENTED YET (phase P3).",
        },
      },
    ],
    "limits": {
      "maxLimit": 5000,
      "maxChangesDefault": 200,
      "maxBodyBytes": 8388608,
    },
    "features": [
      "analytics",
      "ingest.prepared",
      "ingest.raw",
      "goal_templates",
      "undo",
    ],
  },
}
```

This is how a client avoids guessing. A CLI that wants `POST /analytics/runway` checks `features`,
and if it is absent it says _"this server build does not have the analytics plane — update it"_
rather than surfacing a 404 the operator has to decode.

**The table is generated from the same array the router is built from.** There is no second list
(the mistake mcp.mdx §9.3 names). A route present in one and missing in the other is impossible by
construction, and a test walks every published entry and asserts it answers rather than falling
through to the terminal 404.

### 6.3a `status` — `live` and `planned` (LOCKED)

Every route publishes `status`. `live` means implemented. **`planned` means mounted, tiered and
gated, with a handler that refuses `not_ready` naming the phase that will build it.**

Planned routes exist for one reason: the gate ladder in front of a route is the part most worth
testing and the part least likely to change, and gates 4 and 6 cannot be integration-tested through
a real route until a phase that has one. Declaring `POST /sync` as planned means the write-tier
refusal is exercised end to end — through the real router, the real auth middleware and the real
envelope — from P0 rather than from P3.

`status` is published precisely so this cannot mislead: a client reading the route table sees that
`/sync` is planned and does not come away believing it works, which would be the server describing
itself incorrectly — the exact failure this section exists to prevent.

## 7. The write protocol

### 7.1 The three switches and the token (LOCKED)

Four things must be true before one transaction changes:

1. `ACTUAL_MACHINE_ALLOW_WRITE=1` on the server.
2. The client's own switch (`--write`, or `ABMCP_ALLOW_WRITE=1`).
3. `dry_run: false` in the call.
4. `confirm_token` echoing the token the matching plan returned.

Plus a ceiling: `max_changes`, default **200**, and a refusal over it **reports the real count**, so
the operator learns the size rather than being told "too many".

### 7.2 `dry_run` is the default, and the preview is the write (R4)

Every write route accepts `dry_run`, and **it defaults to `true`**. A call with no `dry_run` changes
nothing and returns what it would have done.

The preview is produced by the _same_ code path as the write. For imports this is literally
`importTransactions(..., { dryRun: true })`, which runs the whole real reconciliation — `imported_id`
lookup, the rules engine, fuzzy date/amount matching, split handling — and returns
`{ added, updated, updatedPreview }` without writing. For everything else it is the same handler
inside a transaction that is rolled back.

**Rejected: a `predictChanges()` function.** A second implementation that guesses what the first one
will do disagrees with it at exactly the edges that matter — fuzzy matches, reconciled rows, split
parents — and the disagreement surfaces as a plan that says 117 and an apply that does 131.

The two routes that have **no** `dry_run`, and say so in their schema rather than accepting a flag
they would ignore: `POST /sync` (nothing to preview) and `POST /undo` (the preview is the thing
itself).

### 7.3 The confirm token

A dry run returns:

```jsonc
{
  "ok": true,
  "data": {
    "dry_run": true,
    "changes": { "added": 117, "updated": 12, "unchanged": 1742 },
    "confirm_token": "cf_01J8…", // opaque, 128 bits, this process only
    "expires_at": "2026-09-20T19:11:02Z", // 10 minutes
    "fingerprint": "sha256:7ab3…", // of the exact change set
  },
}
```

The real call passes `dry_run: false` and that token.

- **Ten-minute expiry**, then `conflict` with the hint to re-plan.
- **The change set is recomputed at apply time and compared against `fingerprint`.** If the world
  moved — someone categorised a transaction in the browser, a sync landed — the token is refused with
  `conflict` and the _new_ counts, so nobody applies an hour-old plan against a changed budget.
- **The token is in-process only.** It is not persisted, not derived from the key, and does not
  survive a restart. It proves "you read the plan I just produced", which is the only thing it is for.
- A model cannot invent it. That is the actual mechanism: the write path _requires having read the
  preview_, and no amount of confident guessing substitutes.

### 7.4 Batch

`POST /batch` takes an ordered list of write operations and runs them inside one
`batchBudgetUpdates()`, so the engine's spreadsheet recalculates once rather than N times — the
difference between setting 60 category amounts in 400 ms and in 30 s.

```jsonc
{
  "dry_run": true,
  "max_changes": 200,
  "operations": [
    {
      "op": "budget.set_amount",
      "month": "2026-09",
      "category_id": "…",
      "amount": -45000,
    },
    {
      "op": "budget.set_amount",
      "month": "2026-09",
      "category_id": "…",
      "amount": -12000,
    },
  ],
}
```

- One `confirm_token` for the whole batch.
- **All or nothing.** A failure rolls the batch back and reports the index that failed and why.
- `op` names are the route's own family and verb, from a closed set published in `/capabilities`.
- The ceiling counts _changes_, not operations.

### 7.5 Undo

`POST /undo` and `POST /redo` reach loot-core's own undo stack — the same one `Ctrl-Z` drives in the
browser, which is why every mutating engine handler in the app is wrapped in `undoable()`.

- The response names what was undone.
- The stack is the app's, shared with the browser. Undoing from a program undoes whatever was last
  done _by anyone_, so the route returns the description first and the operator (or the agent's
  human) decides.
- Undo is a **write**-tier route. It is also the single most valuable route on this plane for an
  operator who has just let an agent write, and it is built in phase P4, not "later".

### 7.6 What writes never do

- **Never delete without the admin tier.** Transactions, accounts, categories, payees, rules,
  budget files — every destructive delete is admin, and the MCP does not have it.
- **Never write outside the budget and the staging directory.** The only filesystem writes this
  plane performs are under `{STATEMENTS_ROOT}/{STAGING}/` (§11.3) and `~/T/_actual_budget/` (logs).
- **Never invent a value.** No plug transaction to make a reconciliation balance, no guessed
  category, no rounded amount. A reported gap is recoverable; a fabricated ledger row is not.

## 8. The route catalogue

Conventions for every table below:

- **Tier** is `R` read · `W` write · `A` admin.
- `:id` accepts an id. Where a name is a reasonable alternative, the route also accepts
  `*_name` in the body or query and resolves it, failing with `invalid_input` and the candidates if
  it is ambiguous. Named lookups are a convenience for humans and models; ids are the contract.
- Every route accepts the universal query arguments in §5.5 where it returns a list.
- **Engine** names the `@actual-app/api` method or loot-core handler the route calls (R1).

### 8.0 The plane itself

| Route           | M   | Tier | Arguments | Answers                                                                                                    |
| --------------- | --- | ---- | --------- | ---------------------------------------------------------------------------------------------------------- |
| `/ping`         | GET | R    | —         | liveness, key fingerprint, write tier, server version                                                      |
| `/whoami`       | GET | R    | —         | install path, budget id + name, engine state, tiers, key fingerprint, statements root (configured or null) |
| `/capabilities` | GET | R    | —         | §6.3                                                                                                       |
| `/health`       | GET | R    | `probe`   | engine loaded? budget open? which budgets exist? what to do next                                           |
| `/schema`       | GET | R    | `table`   | the AQL tables and fields `/query` may name (§13). **Phase P2 — see below**                                |

`/ping` versus `/health`: ping proves _the plane is mounted and the key is right_; health proves _the
app can answer a question about a budget_. A green health with a 401 from ping is the most likely
first-run failure and it has to be distinguishable.

**`/ping`, `/whoami`, `/capabilities` and `/health` answer WITHOUT an initialised engine**, and that
is the design rather than an accident: their job is to report what is wrong, and a diagnostic route
that needs the thing it is diagnosing is no diagnostic at all. The engine initialises lazily, on
first use by a route that needs it (§15).

**`/health?probe=true`** is the exception that proves the rule. A lazy engine means the plain check
can otherwise only report "not started yet", so `probe` deliberately attempts initialisation and
reports the outcome — a failed probe comes back `200` with the reason and the remediation, never as
a thrown error. It defaults to **false**, so the ordinary health check stays free of the dependency
it is reporting on.

**`healthy` is deliberately narrow**: an engine that is up with _no budget open_ is not healthy for
the purpose any caller has in mind, and answering "ok" there is how a model concludes that an empty
result means no transactions rather than no budget.

**No budget is ever guessed.** With exactly one budget file and no configured id, that one is
opened. With two or more and no `ACTUAL_MACHINE_BUDGET_ID`, **nothing** is opened, and every route
that needs a budget refuses while naming the ids that exist. Choosing a budget on the operator's
behalf is the worst mistake available on this plane (mcp.mdx §3).

**`/schema` moved to phase P2** — a change this spec learned from building. The AQL schema lives in
loot-core and is **not exposed through `@actual-app/api`**, which exports `aqlQuery` but not the
table definitions. `/schema` therefore needs either a new engine export or engine-backed
introspection; both are the query family's work, and shipping it meanwhile would mean publishing a
table list maintained by hand here — a second copy of loot-core's schema, free to drift.

numbers, one of which the engine produced; there is no judgement in it, which is why it is allowed
to be composed.

- **`uncategorized: true` is a first-class filter**, not a client-side scan. "What have I not
  categorised?" is the single commonest real question and it must not cost 5,000 rows of transfer.
- **`filter{}` on a bulk write takes the same shape as the `GET` query.** One filter language, so
  "show me these" and "change these" cannot select different sets. A bulk write with a `filter`
  always dry-runs first by default and reports the exact count.
- **`run_rules` defaults true on `POST /transactions`**, because that is what the UI does and a
  program adding a transaction should get the same categorisation a human would.
- **`learn_categories` defaults false.** Teaching the rules engine from a bulk program write is a
  side effect nobody asked for.
- **Splits go through `subtransactions[]` on the parent**, never as separate rows with a parent id;
  the engine owns that invariant.

## 10. The analytics plane

### 10.1 Why it exists (LOCKED)

Upstream computes reports in React — `packages/desktop-client/src/components/reports/` — over rows
it pulls with AQL. That is fine for a browser and fatal for us: the thin-client rule says a client
never sums, and "what did I spend on groceries this year" is a sum.

So the sums move here, into the engine, once. Three consequences, all intended:

- The CLI, the MCP and the browser agree on a total because there is one implementation.
- A model never does arithmetic on money. It asks a question and repeats an answer. This is the
  single highest-value safety property in the whole stack.
- A ten-year aggregate is one HTTP call returning 120 rows, not 12,007 rows the caller must reduce.

### 10.2 The routes

All read-tier. All take `start` and `end` (`YYYY-MM-DD`, inclusive), and optional
`account_ids[]`, `category_ids[]`, `exclude_category_ids[]`, `include_offbudget` (false),
`include_transfers` (false).

| Route                              | Extra arguments                                                                | Answers                                                               |
| ---------------------------------- | ------------------------------------------------------------------------------ | --------------------------------------------------------------------- |
| `/analytics/spending-by-category`  | `interval` (month\|quarter\|year\|none), `group_by` (category\|group), `top_n` | the bar chart                                                         |
| `/analytics/income-vs-expense`     | `interval`                                                                     | in, out, net, per interval                                            |
| `/analytics/cash-flow`             | `interval`                                                                     | opening, in, out, closing, per interval                               |
| `/analytics/net-worth`             | `interval`                                                                     | assets, liabilities, net, per interval, per account                   |
| `/analytics/category-trend`        | `category_id`, `interval`                                                      | one category over time, with mean and median                          |
| `/analytics/payee-leaderboard`     | `top_n` (20), `direction` (out\|in)                                            | who got the money                                                     |
| `/analytics/budget-performance`    | `months[]`                                                                     | budgeted vs spent vs balance per category per month, and the variance |
| `/analytics/recurring`             | `min_occurrences` (3), `tolerance_days` (3)                                    | detected subscriptions and their annualised cost                      |
| `/analytics/runway`                | `basis` (3\|6\|12 months)                                                      | on-budget liquid balance ÷ trailing average outflow, in months        |
| `/analytics/uncategorized-summary` | —                                                                              | count and total of uncategorised, by account and by month             |
| `/analytics/anomalies`             | `z` (2.0), `min_amount`                                                        | categories and payees unusually far from their own trailing norm      |

### 10.3 The rules these obey

- **Every figure is integer cents**, and every count is an integer. No percentages are returned as
  floats — a share is returned as its two integers (`amount` and `total`) and the _presentation
  layer_ divides.
- **Transfers are excluded by default.** Counting a transfer from Checking to Savings as spending
  is the classic way a personal-finance tool doubles someone's expenses. `include_transfers: true`
  exists, and the response always echoes which it did.
- **Off-budget accounts are excluded by default**, and the response says so. A brokerage account in
  a spending chart is noise.
- **Every response carries its own provenance**: the resolved date range, the account ids actually
  included, the filters applied, and the row count. A number that cannot say what it counted is a
  number nobody should paste into a decision.
- **`/analytics/recurring` and `/analytics/anomalies` are detectors, not oracles**, and they say so
  in their response: each item carries the evidence (the occurrences, the trailing mean, the
  deviation) so the caller can show its work rather than assert a conclusion.
- Implementation is AQL inside the engine — the same query layer the reports use — so a fix upstream
  is a fix here.

## 11. The ingest plane — statements into the budget

The flagship. cli.mdx §10 describes the operator-facing pipeline; **this section is the engine
behind it**, and it has one significant addition cli.mdx does not have: the _prepared tree_.

### 11.1 Two modes, because two kinds of tree exist

| Mode           | Input                                                                                                                       | What we do                                                        |
| -------------- | --------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| **`prepared`** | a tree that already holds importable files (`.ofx` / `.qfx` / `.csv` / `.qif` / CAMT `.xml`) and a manifest describing them | read the manifest, hand the files to Actual's own parser, import  |
| **`raw`**      | a tree of statement PDFs and text sidecars                                                                                  | extract → normalise → de-duplicate → stage → import (cli.mdx §10) |

**`prepared` is the primary mode and is built first**, because a real archive is usually already
prepared: someone's export pipeline, their bank's own downloads, or a previous extraction run has
already produced OFX. Re-extracting from PDF what a `FITID` already carries is strictly worse — the
bank's own id is the best dedupe key that will ever exist for that row.

`raw` is for the statements that only ever existed as paper.

**A note on where the prepared tree's own conventions come from.** A prepared tree is _not ours_. It
was produced by whatever pipeline the operator ran, it is audit evidence, and this plane treats it as
**strictly read-only** — we never write into it, never move a file in it, and never rewrite its
manifest. §11.3's staging directory is the only place we write, and §11.2's conflict rule exists
precisely because a real archive already has a directory called `import/` that means something else.

### 11.2 The manifest

A prepared tree describes itself with a manifest — a CSV (or JSON) with one row per account. The
route does not care what produced it; it cares about these columns, and it reports any it could not
find rather than guessing:

| Column                                        | Required | Meaning                                                |
| --------------------------------------------- | -------- | ------------------------------------------------------ |
| `entity`                                      | ✅       | the legal person or company the account belongs to     |
| `institution`                                 | ✅       | the bank                                               |
| `label`                                       | ✅       | the account's name in the archive                      |
| `last4`                                       | ✅       | the account number's last four digits                  |
| `kind`                                        | ✅       | `checking` · `savings` · `card` · `brokerage` · `loan` |
| `path`                                        | ✅       | the account's directory, relative to the tree root     |
| `transactions`, `statements`, `first`, `last` | —        | counts and coverage, used for the plan's preview       |
| `reconciled`, `recon_na`                      | —        | how many statements balanced; surfaced as a warning    |

```jsonc
// GET /ingest/manifest?root=…   (read)
{
  "ok": true,
  "data": {
    "root": "{STATEMENTS_ROOT}", // resolved from the credentials file unless overridden
    "manifest_path": "import/accounts.csv",
    "mode": "prepared",
    "accounts": [
      {
        "entity": "household",
        "institution": "Northbank",
        "label": "Checking_x4021",
        "last4": "4021",
        "kind": "checking",
        "path": "bank/household/Northbank/Checking_x4021",
        "statements": 21,
        "transactions": 368,
        "first": "2024-10",
        "last": "2026-06",
        "files": {
          "combined": "Checking_x4021_ALL.ofx",
          "monthly": 21,
          "formats": ["ofx", "csv"],
        },
        "warnings": [],
      },
    ],
    "totals": { "accounts": 27, "transactions": 12007, "unreconciled": 12 },
  },
}
```

**Conflict rule (LOCKED).** If the manifest's own directory is named `import/`, the staging
directory **must not** be `{ROOT}/import/`. The route refuses to stage into a directory that already
holds the operator's archive and returns `conflict` naming both paths. cli.mdx §10.7's staging
layout is correct in shape and wrong in one detail — the default staging path is
**`{ROOT}/.actual-staging/`**, and `{ROOT}/import/` is only used when it is demonstrably ours (it
contains our `_manifest.csv` and no foreign files). Losing somebody's audit evidence to a name
collision is not a bug we are willing to have once.

### 11.3 The staging directory

```
{ROOT}/.actual-staging/
├── _manifest.csv     one row per source file ever seen
├── _rows.csv         every de-duplicated row, across every account
├── _dupes.csv        what was collapsed, and the rule that collapsed it
├── _conflicts.csv    the cases that block an apply
├── _run.log          append-only: run id, timestamp, counts, outcome
└── {ENTITY}/{INSTITUTION}/{ACCOUNT}/{YYYY}-{MM}.csv
```

- **Rebuildable at any time.** Deleting it loses nothing but time, and nothing downstream may treat
  it as a system of record.
- **Atomic per file** (temp + rename), so an interrupted run never leaves a half-written CSV that a
  later run imports.
- **Gets a `.gitignore` containing `*` on first write**, because the statements tree is usually
  itself a git repo and these are derived files full of real financial data.
- In `prepared` mode the staging directory holds only the run log and the plan — the importable
  files are already the operator's, and we do not copy them.

### 11.4 The routes

| ------------------------ | ---- | ---- | -------------------------------------------------------------------- |

ceiling.

### 11.5 Two layers of de-duplication

**Layer one, the statement level.** The same month scanned twice, under two filenames, is one
statement. Grouping is on `(entity, institution, last4, statement_period)` read from _inside_ the
document, never from the directory name. Identical bytes → `duplicate_identical`. Different bytes,
same period → ranked by source quality, the loser marked `superseded`, and both recorded. Two
statements that disagree about a _transaction_ → `conflict`, which blocks that account and names
both files. Parsing both is how an archive doubles a month.

**Layer two, the transaction level.** A deterministic `imported_id` per row, which is what makes a
re-run idempotent.

- In **prepared** mode the id is already there — OFX's `FITID`, which Actual maps straight to
  `imported_id`. **We use the bank's id and never mint our own over the top of it.**
- In **raw** mode we mint one, from the row's own content plus its ordinal within its statement:
  `{last4}-{YYYYMMDD}-{amount_cents}-{ordinal}-{sha1_8(normalised_description)}`.

**The ordinal is scoped to the statement, and the scope is the whole trick.** Two genuine $5.00
coffees on the same day at the same shop get ordinals 0 and 1, so they get two ids and both import.
The scope must be the _statement_, not the calendar month, because cycle-dated accounts (a card
running the 15th to the 14th) feed one calendar month from two statements, and month-scoped ordinals
would renumber them into collisions on a re-run. There is a fixture for exactly this.

### 11.6 Actual's importer is the authority (LOCKED — R7)

We never decide what is a duplicate. `importTransactions` does, and the plan is **its** dry run.

`plan` and `apply` are **the same call with one boolean different**. `opts.dryRun` becomes
`isPreview: true` on `reconcileTransactions`, which runs the entire real reconciliation —
`imported_id` lookup first, then the rules engine, then fuzzy date/amount matching, then split
handling — and returns `{ added, updated, updatedPreview }` with nothing written. The counts we
report are read straight out of that: `added.length`, `updated.length`, and `updatedPreview`
partitioned by `ignored` and by whether the match carried an `imported_id`.

**Rejected: query the ledger for our `imported_id`s and subtract.** It is the obvious
implementation, it is a second reconciliation engine, and it disagrees with the first one at the
edges — fuzzy matches, reconciled-and-locked rows, split parents. The disagreement surfaces as a
plan that says 117 new and an apply that adds 131, which is the exact failure this whole design
exists to prevent.

**The plan is recomputed at apply time, never replayed.** The `confirm_token`'s fingerprint covers
the change set; if the budget moved underneath it, the apply refuses with the new counts (§7.3).

### 11.7 The importer options are pinned (LOCKED)

Two of Actual's defaults are wrong for a bulk archive import, and both are pinned here rather than
left to a caller:

| Option             | Default | **Ours**    | Why                                                                                                                                                                                                    |
| ------------------ | ------- | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `reimportDeleted`  | `true`  | **`false`** | The operator deleted that row on purpose. An import that resurrects deleted transactions on every run is an import nobody runs twice. Overridable per call, and the override is named in the response. |
| `strictIdChecking` | `true`  | **`true`**  | Loose matching lets two statement rows one day and one cent apart match each other. With real ids present, strict is correct and the fuzzy fallback is a liability.                                    |
| `defaultCleared`   | `true`  | `true`      | A row that appeared on a statement has cleared. That is what a statement is.                                                                                                                           |

`imported_payee` carries the **raw** description, unmodified, and `notes` is **left alone** — it is
the operator's field, and an import that overwrites a note they typed has destroyed the only data in
the row a human authored. There is a test that writes a note, re-runs the pipeline so the row is
updated, and asserts the note survives byte for byte.

### 11.8 What ingest never does

- Never writes, moves, renames or deletes anything under `{ROOT}` outside the staging directory.
- Never deletes a transaction. The pipeline is additive; removing is a human act in a UI.
- Never guesses a category. Categorisation is the rules engine's job and it runs on import because
  the rows go through the app's importer.
- Never invents a date, an amount, or a balancing row. An unreadable row is named in
  `_conflicts.csv` and counted — never silently dropped, never rounded into existence.
- Never uploads a statement anywhere. Extraction is local, and the plane has no egress.

## 12. Account provisioning from a manifest

The question _"create the accounts for my archive"_ deserves its own section, because it is the
first thing that happens on a new budget and the easiest thing to get expensively wrong.

### 12.1 `POST /ingest/accounts/plan` (read)

Reads the manifest, reads the budget's existing accounts, and returns a per-row decision with its
reasoning. It **creates nothing**.

```jsonc
{
  "ok": true,
  "data": {
    "plan": [
      {
        "manifest": {
          "entity": "household",
          "institution": "Northbank",
          "label": "Checking_x4021",
          "last4": "4021",
          "kind": "checking",
        },
        "action": "create",
        "proposed": {
          "name": "Household · Northbank Checking ••4021",
          "type": "checking",
          "offbudget": false,
        },
        "reason": "no existing account matched on last4 or name",
      },

      {
        "manifest": {
          "entity": "household",
          "institution": "Meridian",
          "label": "Retirement",
          "kind": "brokerage",
        },
        "action": "create",
        "proposed": {
          "name": "Household · Meridian Retirement",
          "type": "other",
          "offbudget": true,
        },
        "reason": "kind=brokerage → off-budget by the on_budget_kinds rule",
        "warnings": ["source is monthly aggregate, not per-trade"],
      },

      {
        "manifest": {
          "entity": "acme_llc",
          "institution": "Northbank",
          "label": "Checking_x7734",
          "last4": "7734",
        },
        "action": "link",
        "existing": { "id": "5a0e…", "name": "Acme LLC Checking" },
        "reason": "matched on last4 7734",
      },
    ],
    "summary": { "create": 24, "link": 3, "ambiguous": 0 },
    "confirm_token": "cf_01J8…",
  },
}
```

`action` is one of `create` · `link` · `skip` · `ambiguous`. **`ambiguous` never becomes a create.**
It is returned with every candidate and it blocks that row until the caller resolves it — two
accounts sharing a last4 across two entities is the normal case in a real archive, not an edge one.

### 12.2 The naming rule

The default is `"{Entity} · {Institution} {Kind} ••{last4}"`, and it is a _default_, overridable per
call with a `naming` template and per row with an explicit `name`. Three properties matter:

- **It disambiguates.** Two entities both bank at the same institution and both have a Checking; without the
  entity, one of them silently receives the other's decade.
- **It is stable.** Re-running the plan against a budget that already has these accounts yields
  `link`, not a second set with `(2)` on the end.
- **It carries the last4**, so a human can check a row against a paper statement in one glance.

### 12.3 On-budget versus off-budget

| `kind`      | Default                   | Why                                                          |
| ----------- | ------------------------- | ------------------------------------------------------------ |
| `checking`  | on-budget                 | money you spend                                              |
| `savings`   | on-budget                 | still yours to allocate                                      |
| `card`      | on-budget, `type: credit` | the liability belongs in the budget; the balance is negative |
| `brokerage` | **off-budget**            | market movement is not income and would wreck every report   |
| `loan`      | **off-budget**            | tracked for net worth, not budgeted against                  |

Controlled by `on_budget_kinds[]`, echoed in the response, and explained per row in `reason`. Getting
this wrong is not a small mistake: a brokerage account marked on-budget turns every market swing into
budgetable income.

### 12.4 `POST /ingest/accounts/apply` (write)

Takes the token, creates the `create` rows in one batch, links the `link` rows into the map file, and
returns the created ids alongside the manifest rows they came from. It then **writes the map**
(§11.4) beside the statements, so the very next call to `/ingest/plan` has a complete mapping and the
operator never hand-writes a YAML file of 27 account ids.

`dry_run` defaults true here too. The first real run of a ten-year archive is supposed to be a
deliberate act.

## 13. The query escape hatch

`POST /query` takes one ActualQL query. It exists so a question nobody anticipated does not require a
new route, and it is guarded so it cannot become a back door.

| Guard            | Rule                                                                                                                                            |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Read-only        | `SELECT` shape only. No mutation verb parses.                                                                                                   |
| Single statement | One query per call; a `;` is a parse error, not a second statement                                                                              |
| Table allowlist  | `transactions` · `accounts` · `categories` · `category_groups` · `payees` · `schedules` · `rules` · `tags` · `zero_budgets` · `reflect_budgets` |
| Denied, by name  | anything holding a secret or a sync internal; the refusal **names the typed route that does expose it**                                         |
| Row cap          | `limit`, default 200, cap 5,000, clamped and reported                                                                                           |
| Byte cap         | 1 MiB; over it, `truncated` and a narrowing hint                                                                                                |
| Timeout          | 10 s                                                                                                                                            |

`GET /schema` returns the tables and fields the allowlist permits, with types, **so a caller does not
guess.** A model that has read `/schema` writes a query that runs; a model that has not writes three
that do not.

**`/query` is a last resort, and its own description says so.** If a question is asked twice through
`/query`, that is a signal it should be a route in §8 or §10 — and adding it there is cheap, because
a route is a handler and a schema entry.

## 14. Money, dates and identifiers

### 14.1 Integer cents, everywhere (LOCKED — R2)

`-12350` is `-$123.50`. Every amount in every argument, every response field, and every intermediate
value is a **signed integer number of cents**. Negative is money out.

- **No floats. Not once, not "just for this one field".** `0.1 + 0.2 !== 0.3`, and a rounding error
  in a budget is a wrong number in somebody's life.
- **No decimal strings on the wire either.** `"123.50"` invites a parse on the other side, and the
  other side is sometimes a language model.
- The **only** conversion point is `money.ts`, and the _clients_ call it for display. `--format json`
  and every MCP response carry the raw integer.
- A test round-trips a list of adversarial values — `-1`, `0`, `1`, `99`, `-99`, `100000000`,
  `Number.MAX_SAFE_INTEGER` — through every layer.

### 14.2 Absent is not zero (LOCKED — R3)

A category with **no budget entry** returns `budgeted: null`. A category budgeted at zero returns
`budgeted: 0`. They are different facts and a budgeter acts differently on each: `null` means "you
have not decided", `0` means "you decided nothing".

The same rule applies everywhere absence is possible: a balance we could not compute is an error, not
`0`; a date range with no transactions returns an empty array and a `count: 0`, never a fabricated
row of zeros; an account with no transactions has `balance: 0` (which is a real balance) and
`first_transaction: null` (which is a real absence).

`GET /budget/month/:m/gaps` exists to turn this rule into an answer: _these categories have spending
and no budget entry_, which is the most useful single question on a budget page.

### 14.3 Dates

`YYYY-MM-DD` on the wire, always, and months are `YYYY-MM`. Ranges are **inclusive on both ends** and
every response echoes the range it resolved. No relative dates on the wire — "last month" is the
client's job to resolve, and the response says which month it decided, so a call made at 23:59 on the
31st is auditable.

### 14.4 Identifiers

UUIDs from the engine, opaque to every caller. Where a name is accepted instead, the resolution is
exact-match-first, then case-insensitive, and **ambiguity is an error carrying the candidates** —
never a silent pick of the first.

## 15. Concurrency, limits and performance

- **One engine instance, one budget open.** Loading a different budget is a write with global effect
  (§8.1).
- **Writes are serialised, concurrency 1.** Two concurrent writes against one budget is a conflict
  the CRDT layer should not be asked to arbitrate on our behalf. A second write waits; if it waits
  past its timeout it gets `conflict` with a retry hint, never a partial apply.
- **Reads are unbounded** and do not block on a write.
- **No cache anywhere on this plane.** The engine holds the budget; a cache here would be a second
  copy that can be stale, and the entire point of the design is that there is no second copy of
  anything.
- **Long routes stream progress.** `/ingest/apply` and `/ingest/extract` can run for minutes.
  They accept `Accept: application/x-ndjson` and emit progress lines, ending with the normal
  envelope as the last line — so a client can render a progress bar and never look hung. With plain
  `Accept: application/json` they simply take as long as they take, and **there is no server-side
  timeout on them**.

| Limit                    | Value       | Behaviour over it                        |
| ------------------------ | ----------- | ---------------------------------------- |
| `limit` on a list        | cap 5,000   | clamped, `truncated: true`               |
| Response bytes           | 8 MiB       | `truncated: true` + narrowing hint       |
| Request bytes            | 8 MiB       | `invalid_input`                          |
| `max_changes` on a write | default 200 | `conflict`, **reporting the real count** |
| Per-call timeout         | 30 s        | `upstream_error`; ingest routes exempt   |
| `/query` timeout         | 10 s        | `upstream_error`                         |

## 16. Security

### 16.1 Threat model

| #   | Threat                                              | Control                                                                                         |
| --- | --------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| 1   | Another computer reaches port 5006                  | Gate 1, on the real socket address, not `X-Forwarded-For`                                       |
| 2   | A web page the operator has open calls the plane    | Gate 2 (origin + host) and gate 3 (the key it cannot read)                                      |
| 3   | Another user on this machine                        | Gate 3; the key file is 0600 and ownership-checked                                              |
| 4   | An agent writes something the operator did not want | Gates 4 and 6: two tier switches, `dry_run` default, a token only a plan can produce, a ceiling |
| 5   | A malicious payee name or memo steers a model       | §16.3 — untrusted fields are marked, never executed                                             |
| 6   | A secret leaks into a log, an error or a context    | §16.4 — fingerprints only, generic internals                                                    |
| 7   | A bad plan is applied against a changed budget      | §7.3 — fingerprint recomputed at apply                                                          |
| 8   | The operator's archive is damaged                   | §11.2's conflict rule and §11.8's never-list                                                    |

### 16.2 What is never exposed

The sync server's password or its hash; the budget's end-to-end encryption key; OAuth tokens or
secrets for any bank-sync provider; the `secret-set` / `secret-check` handlers; absolute filesystem
paths outside the statements root; environment variables; SQL strings; stack traces.

There is a **canary test** that calls every route in `/capabilities` against a fixture budget and
greps every response for the key pattern, for `secret`, for `password`, and for `/Users/`.

### 16.3 Prompt-injection posture

A payee name, a transaction note, an account name and a statement description are **operator-supplied
data that may have been written by a third party** — a merchant chose that descriptor, not the
operator.

- Responses mark them: `meta.untrusted: ["payee", "notes", "imported_payee", "account_name"]`.
- The plane never interprets them as instructions, never uses them to choose a route, and never
  reflects them into a `hint`.
- [ai/mcp_prompt.md](../ai/mcp_prompt.md) carries the matching instruction on the model's side: text
  from the ledger is _evidence about money_, never a directive.

### 16.4 The audit trail

Every write appends one line to `~/T/_actual_budget/machine.audit`:

```
2026-09-20T18:41:02.118Z  route=/ingest/apply  tier=write  caller=mcp  budget=8c1e…  token=cf_01J8…  changed=117  ok=true  took_ms=8412
```

No amounts, no payees, no account names — **what happened, not what it was about.** The file is the
answer to "what did the agent do last Tuesday" and it is not a second copy of the ledger. `caller`
comes from an optional `X-Actual-Client` header and is advisory: it is for reading a log, never for a
decision, because a header is not an authentication.

## 17. Open-source safety (LOCKED)

This repo is going public. Three rules, each with a test:

1. **No secret in the tree.** There is no config key anywhere under `src/machine/` that can hold a
   key, password or token. A test greps the built output for 32-plus-character hex literals.
2. **No private path in the code.** The statements root, the budget id, the entity names and the
   account last-fours are **all configuration, none constants**. **Every entity name, institution
   name and account number appearing anywhere in this spec is invented** — `household`, `acme_llc`,
   `Northbank`, `Meridian`, `••4021` — and is there to show a shape, never to record a real one. A test greps the source for
   `/Users/`, for the archive directory name, and for the entity names used on this machine, failing
   on a hit outside a fixture or a documentation comment. **The example values in this spec are
   illustrations of configured values; none of them is a default in code.**
3. **No financial data in the repo.** The statements tree and the staging directory are outside the
   repo by construction, and the staging directory writes its own `.gitignore` anyway. Fixtures use
   synthetic statements with invented banks and invented amounts, committed deliberately.

The repo's PR and commit rules apply to every change here — `[AI]` prefix on commits and PR titles,
the PR template left blank, no GitHub issues created by an agent. See
[.github/agents/pr-and-commit-rules.md](../.github/agents/pr-and-commit-rules.md).

## 20. Acceptance criteria

The plane is done when all of these hold:

1. `GET /ping` answers with a valid key and 404s without one, from a cold `just server-bg`.
2. `GET /capabilities` lists every mounted route, and the coverage fixture in §9 matches it exactly.
3. Every route in §8 exists, validates its input, and returns the envelope — including its errors.
4. **Every ✅ cell in §9's matrix is exercised by a test** that performs the action and asserts the
   budget changed the way the UI would have changed it.
5. Every write defaults to `dry_run: true`, refuses without a token, and reports the real count when
   it refuses on the ceiling.
6. `/ingest/plan` and `/ingest/apply` report identical counts over an unchanged budget.
7. A full archive import of the fixture tree is idempotent: the second run adds zero.
8. `POST /undo` restores the budget to a byte-identical state after every write route.
9. No float, no decimal string and no `parseFloat` appears in any response or any handler.
10. The gate ladder's full negative suite passes, including the `X-Forwarded-For` and `Origin` cases.
11. The leak canary passes across every route.
12. The three open-source canaries pass against the built output.
13. `just build && just server-bg && abx doctor` is green on a machine that has never run this before,
    with no manual key step.

## 22. Invariants recap (LOCKED)

1. Loopback only, forever. No flag changes it.
2. 256 bits from a CSPRNG, 64 hex characters, in a 0600 file in the home directory, never in the repo.
3. The key is compared in constant time and never logged except as a fingerprint.
4. Five gates before any handler, six before any write. Fail closed at every one.
5. One envelope. Nine error codes. Every error names a fix.
6. Money is an integer number of cents, everywhere, always.
7. `null` is not `0`. Absence is a fact and it is reported as one.
8. Every write has a dry run, and the dry run is the write with one boolean different.
9. A write needs two tier switches, a `dry_run: false` and a token it could only get from a plan.
10. Actual's importer is the sole authority on what is a duplicate.
11. One engine call per route; composed routes say so and are named in this spec.
12. Nothing is computed twice. If a client would have to sum it, it becomes a route here.
13. Every cap is reported. No silent truncation, ever.
14. Nothing outside the staging directory and the log directory is ever written.
15. Deleting is admin-tier, and the MCP does not have it.
16. No secret, no private path and no financial data in this repo.
